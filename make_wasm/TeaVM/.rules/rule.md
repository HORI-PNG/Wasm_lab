# 作業ルール

このフォルダ（`make_wasm/TeaVM`）で作業するときのルール。Claude はこのルールに必ず従う。

## 1. 作業の流れ：計画 → 確認 → 実行 → 記録 → 理解の確認

**ユーザーが計画を確認して承認するまで、作業（コードの変更・ビルド・コミットなど）を始めない。**

```
① 計画を書く      next-plan/stepNN-内容.md を作る（まだ実行しない）
② 確認してもらう  ユーザーが読んで、承認・修正・却下を決める
③ 実行する        承認されたら、その計画どおりに作業する
④ 記録する        logs/stepNN-内容/Artifact.md に、やったことと結果を書く（最後に「確認用コマンド」をまとめる）
⑤ 片付ける        実行した計画の md は logs/stepNN-内容/plan.md に移す（next-plan/ には未実行の計画だけを残す）
⑥ 保存する        ステップのブランチでコミットし、GitHub に push する（Gitblit へはユーザーが push する。「3. ブランチ」参照）
⑦ 説明する        何をしたかをユーザーに説明し、質問に答える
⑧ 問題を出す      そのステップについての問題を出し、ユーザーが全問に正しく答えられたら次へ進む（「6. 理解の確認」参照）
```

- 「進めたい」「やっていきたい」などの方針の話だけでは、承認とみなさない。**計画の md を示し、そのステップを実行してよいという返事をもらってから**実行する。
- 実行中に計画と違うことをする必要が出たら、作業を止めてユーザーに相談する（計画の md も直す）。
- 1 回の承認で実行するのは、その計画の 1 ステップだけ。終わったら、次のステップの計画を `next-plan/` に書いて、また確認を待つ。
- **ユーザーが前のステップの内容を理解してから、次のステップに進む。** ステップが終わったら説明し、問題を出す。ユーザーが問題に合格するまで、次の計画の承認を求めない。

## 2. 計画の書き方（`next-plan/stepNN-内容.md`）

次の項目を書く。

| 項目 | 内容 |
|---|---|
| 目的 | 何のためにやるか。資料（「P6P7_対策の検討.pdf」など）のどこに対応するか |
| やること | 作業の手順。変更するファイルと、どう変えるか |
| やらないこと | このステップでは扱わない範囲 |
| 確認方法 | 終わったときに何で「できた」と判断するか |
| ブランチ | 作るブランチ名と、どのブランチから作るか |
| 決めてほしいこと | ユーザーに判断してもらいたい点（選択肢と、Claude のおすすめ） |

## 3. ブランチ

- 名前は `stepNN-内容`（NN は 2 桁の番号）。番号順に並び、名前を見れば内容が分かるようにする。
- 各ステップのブランチは、1 つ前のステップのブランチから作る。終わったブランチは消さずに残す。
- `main` は作業前の状態のまま触らない。`step00-baseline` は作業前の状態を保存したブランチ。
- コミットは、そのステップのブランチの上で、ステップが終わったときに行う。
- **GitHub への push は Claude が定期的に行う。** 具体的には次のタイミング。
  - ステップが終わってコミットした直後
  - ルールや記録だけを変えたコミットの直後
- push 先と担当：

  | リモート名 | URL | push する人 |
  |---|---|---|
  | `origin`（GitHub） | `git@github.com:HORI-PNG/Wasm_lab.git` | Claude |
  | `gitblit`（Gitblit） | `https://horinouti@birdcage.mk.ics.kyutech.ac.jp/gitblit/r/~horinouti/wasm_lab.git` | **ユーザー**（Claude は push しない） |

- Claude は `git push -u origin <ブランチ名>` で、ステップのブランチ（`stepNN-内容`）だけを送る。`main` は触らないので push しない。
- Gitblit へ push するためのコマンドは、`Artifact.md` の「確認用コマンド」の最後に書いておく（ユーザーが実行する）。
- **パスワードなどの認証情報は、Claude が扱わない。** チャットで受け取らず、ファイル・コマンド・記録・コミットにも書かない。
- 強制 push（`--force`）はしない。push が拒否されたら、作業を止めてユーザーに相談する。
- push したら、`Artifact.md` に push したブランチとコミットを書く。

## 4. 記録（`logs/stepNN-内容/Artifact.md`）

1 ステップにつき 1 フォルダを作り、その中に `Artifact.md` を置く（Antigravity の Artifact に倣った形）。

```
logs/
├ README.md                     … ステップの一覧（ブランチ・状態）
└ stepNN-内容/
   ├ Artifact.md               … このステップの記録（下の形式）
   ├ plan.md                   … 承認されて実行した計画（next-plan/ から移したもの）
   └ quiz.md                   … 理解の確認の問題と、ユーザーの回答・判定（「6. 理解の確認」参照）
```

`Artifact.md` は次の形式で書く。

1. **概要**：何をしたか（3 行程度）。ブランチ名・日付・承認の有無
2. **タスク**：チェックリスト（終わったものに `[x]`）
3. **実装計画**：どう進めたか、なぜそうしたか
4. **ウォークスルー**：実際にやったこと、実行したコマンド、途中で直したこと
5. **変更したファイル**：ファイルと変更内容の表
6. **検証結果**：何をどう確かめ、どうなったか（失敗も書く）
7. **分かったこと・残った課題**：次のステップに引き継ぐこと
8. **確認用コマンド**（必ず最後に置く）：ユーザーが自分で結果を確かめるために実行するコマンドのまとめ
   - 実行する場所（例：`make_wasm/TeaVM` フォルダ）を最初に書く。
   - コマンドは 1 つずつ別のコードブロック（` ```bash `）に書き、それぞれ「何を確かめるコマンドか」と「期待する結果（どう表示されれば OK か）」を添える。
   - 実行の順番に並べる（例：ブランチの切り替え → ビルド → 検算 → 結果のファイルを見る）。
   - 時間がかかるコマンドは、その目安も書く。

- 作業の途中でも更新する。最後にコミットに含める。
- `logs/README.md` のステップ一覧も更新する。

## 5. コードの書き方

- `org/mklab/nfc`（NFC 本体）は変更しない。必要な処理は `org/example` 側に書く。
- `org/example/generated/` と `webapp/nfc.generated.js` は生成物。直したいときは生成器（`JavaGenerator.py`）かテンプレートを直して再生成する。
- 生成器を変えたら、`verify/run.sh` で検算する。
- Java コードは `var` を使わず明示的な型で書く。コメント・ドキュメントは日本語。

## 6. 理解の確認（問題）

ステップが終わって説明したら、Claude がユーザーに問題を出す。**全問に正しく答えられたら合格**とし、合格してから次のステップの計画の承認に進む。

問題の作り方・採点・記録の詳しい手順は、skill **`step-quiz`**（`.claude/skills/step-quiz/SKILL.md`）に従う。ユーザーは `/step-quiz step01` のように呼び出して、好きなときに問題を出させることもできる。

### 問題の作り方

- 1 ステップにつき **5〜8 問**。次の 3 種類をすべて含める。

  | 種類 | 例 |
  |---|---|
  | 何をしたか | 「このステップで `mainClass` を何から何に変えたか。それで何が変わったか」 |
  | 技術的な質問（なぜ・仕組み） | 「JVM との一致だけでなく、数学的な性質も確かめるのはなぜか」 |
  | 実行内容（コマンドと結果の読み方） | 「`verify/run.sh` の終了コードが 1 のとき、どこを見れば原因が分かるか」 |

- 答えを丸暗記しなくても、そのステップの内容を理解していれば答えられる問題にする。数値や名前をそのまま問うだけの問題は少なめにする。
- 記述式を基本とする。選択式を混ぜてもよい。
- 問題を出す前に、答えを `quiz.md` に書かない（ユーザーがファイルを見ると答えが分かってしまうため）。

### 進め方

1. 問題を `logs/stepNN-内容/quiz.md` に書き、チャットでも示す。
2. ユーザーが回答する。
3. Claude が 1 問ずつ判定し（正解・一部正解・不正解）、それぞれに解説を付ける。
4. 一部正解・不正解の問題は、解説の後に**言い方を変えた問題**を出し直す。正しく答えられるまで繰り返す。
5. 全問正解になったら合格。`quiz.md` に問題・回答・判定・解説を記録し、`logs/README.md` の状態を「理解の確認済み」にする。
6. 合格してから、次のステップの計画（`next-plan/`）の承認に進む。
