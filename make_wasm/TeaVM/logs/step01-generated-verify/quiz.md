## 問題 1（A. 何をしたか）

step01 では、`app/build.gradle.kts` の `mainClass` を何から何に変えましたか。
また、それによって **JS から見て**何が変わり、**NFC の計算の中身**は変わったか・変わらなかったかを、理由とあわせて答えてください。

- 回答：mainClass = "org.example.generated.NfcWasm" へ変更した。以前は手動で作成した（org.example.NfcWasm）ものだった。それによって、JS -> Wasm のエントリーポイントが変化し、対応する機能が増えた。NFCの計算の中身は変わらない。理由は、変化したものがエントリーポイントのみのため。
- 判定：正解
- 解説：手書き版の `org.example.NfcWasm` から自動生成版の `org.example.generated.NfcWasm` に変えた、で合っています。JS から見ると、呼べる関数が 30 個から 69 個に増え、関数の名前も変わりました（例：`determinant` → `realLuGetDeterminant`）。そのため、手書き版用の `nfc.js` は今の wasm では使えません。NFC の計算の中身は変わりません。手書き版も自動生成版も、窓口とブリッジが違うだけで、同じ `org.mklab.nfc` を呼んでいるからです。

## 問題 2（A. 何をしたか）

手書き版のコード（`org.example` の `NfcWasm` や `EigenWasm` など）は、step01 で `mainClass` から外しましたが、消さずに残しました。
残した理由を 2 つ答えてください。

- 回答：手書き版を残すことで、自動生成と手書き版の精度（正答率）の違いを比較することができるため。2つ目はわからない。
- 判定：一部正解
- 解説：1 つ目は合っています。手書き版を「比較の基準」として残し、③ 手書き版との一致（27 組）を確かめました。ただし比べたのは「正答率」ではなく、「同じ入力に対して同じ値を返すか」です。2 つ目は、**計測用の関数（`multiply` / `prepareMultiply` / `multiplyPrepared`）が手書き版にしかない**ことです。WebGPU との速さ比べなどの計測に使う関数で、自動生成版にはまだありません。計測を再開する前に、step03（② 手書きの差し込み口）で自動生成版に加えるための元として残しています。

## 問題 3（B. 技術的な質問）

`JvmReference.java` は、JSON に関数の「答え」だけでなく「**引数**」も書き出しています。
Wasm 側（`wasm-verify.mjs`）で入力を作り直さずに、この引数をそのまま使うのはなぜですか。

- 回答：入力を同じにすることで、正答率を正しく観測することができるため。
- 判定：正解
- 解説：核心の「入力を同じにする」が押さえられています。補足すると、Java 側と JS 側でそれぞれ入力を作ると、作り方のちょっとした違い（行列の並べ方など）で入力が食い違うおそれがあります。そうなると、不一致が出たときに「Wasm への変換のせい」なのか「入力の違いのせい」なのか区別できません。Java が実際に使った引数をそのまま渡せば、**違うのは実行場所（JVM か Wasm か）だけ**になり、不一致の原因を Wasm への変換に絞り込めます。なお、ここで見ているのは「正答率」ではなく、1 回 1 回の答えが同じかどうかです。

## 問題 4（B. 技術的な質問）

検算には「① JVM との一致」と「② 数学的な性質」があります。
① で 207 回すべて完全一致したのに、② も確かめるのはなぜですか。**① だけでは見つけられない間違い**の例を 1 つ挙げて説明してください。

- 回答：返ってきたオブジェクトの形式によって、数値的にはあっているものが不一致となってしまうこと。
- 判定：不正解
- 解説：回答の「形式の違いで不一致になる」は、③ 手書き版との比較で起きたこと（固有値と FFT の 5 組）で、この問題とは別の話です。① は、**同じ Java のコード**を JVM と Wasm で動かして比べます。だから、**コードそのものが間違っていれば、JVM も Wasm も同じように間違え、① では「一致」になってしまいます**。例：自動生成のブリッジが行列を組み立てるときに行と列を取り違えていても、JVM と Wasm は同じ間違った答えを返すので一致します。② は「Q·R を掛けて元の A に戻るか」のように答えそのものの正しさを確かめるので、この種の間違いを見つけられます。また ① は Wasm の関数を直接呼ぶので JS ラッパー（`nfc.generated.js`）を通りませんが、② はラッパーを通すので、ラッパーの変換の間違いも見つけられます。

## 問題 5（B. 技術的な質問）

`JvmReference.java` は、69 個の関数を呼ぶコードを 1 つずつ書いていません。
それでも全部の関数を呼べるのは、
(1) 関数の一覧をどうやって手に入れているか、
(2) 関数ごとの引数（行列・ベクトル・数）をどうやって決めているか、
の 2 点によります。それぞれ説明してください。また、この作りにしたことで、生成器を変えて関数が増えたときに何がうれしいかも答えてください。

- 回答：(1)JavaParserで解析した構文が抽象構文木であり、そのクラスや引数の型を入手している。(2)JavaParserで取得した情報に記載がある。ただし、JSで読み込める型にするために、2次元配列を、1次元+行+列の情報に置き換えるという工夫がある。
- 判定：不正解
- 解説：JavaParser は、**コード生成器がブリッジを作る前に** NFC のソースを解析する道具で、`JvmReference` では使っていません。(1) `JvmReference` は**リフレクション**を使い、プログラムの実行中にクラスを調べます。`Class.forName("org.example.generated.NfcWasm")` でクラスを取り出し、`getDeclaredMethods()` でメソッドを全部取り出し、public・static・`main` 以外、で絞り込みます（69 個）。(2) `getParameterTypes()` で引数の型の並びを見て、`double[]` の後に `int, int` が続けば「行列（1 次元配列・行数・列数）」とみなし、用意した行列を当てはめます。回答の「2 次元配列を 1 次元＋行＋列に置き換える」はブリッジの決まりそのもので、`JvmReference` はその決まりを**逆に使って**型から引数を決めています（この点は合っています）。それ以外の `double[]` はベクトル、ベクトルの直後の `int` はその長さ、など。うれしい点：関数が増えても、**JvmReference のコードを書き足す必要がない**（テストが自動でついてくる）。

### 問題 5''（問題 5' の出し直し）

(1) 次の（ア）〜（ウ）に入る言葉を答えてください。
`Class.forName("org.example.generated.NfcWasm")` は（ア）`名前を指定したクラス` を取り出す。`getDeclaredMethods()` は （イ）`メソッド`を取り出す。このように、プログラムの実行中にクラスやメソッドを調べたり、名前で呼び出したりする仕組みを（ウ）`リフレクション`という。

(2) `realFft` の引数の型の並びは `[double[], int]` です。`JvmReference` の決まりは次のとおりです。

- `double[]` の後に `int, int` が続く → 行列（中身・行数・列数）
- それ以外の `double[]` → ベクトル（用意したベクトルを前から順に使う）
- ベクトルの直後の `int` → そのベクトルの長さ
